### 2.4 ⚠️ 架构冲突：无法直接合并

| 包 | Vue | UI 库 | 构建 |
|---|---|---|---|
| shared-components | **2.x** | Vant 2 / Element UI | Rollup |
| patient/doctor/consultation/assistant | **2.7** | Vux / Vant / AntD | Webpack 4 |
| patient-manage-app | **3.5** | **Vant 3** | **Vite** |

**管理端是 Vue 3 + Vite + Vant 3，与 shared-components 的 Vue 2 + Rollup 不兼容**，无法共用同一份 SFC 产物。

→ 建议拆分为 `@caring/shared-components`（Vue 2，四个 legacy 端共用）+ `@caring/shared-components-v3`（Vue 3，管理端），或统一改用 **Vue 3 + Vant 3 + Vite** 全面升级（工作量极大，不建议在本次演示范围内）。

## 三、演示 Demo 可行性：3 个真实阻塞

### 🔴 阻塞 1：管理端构建失败（唯一硬阻塞）

```
$ cd packages/patient-manage-app && npx vite build --mode prod
✓ 987 modules transformed.
✗ 'hasInjectionContext' is not exported by node_modules/vue-demi/lib/index.mjs
   imported by node_modules/pinia/dist/pinia.mjs
error during build
```

**根因链（已闭环验证）**：

```
pinia@2.3.1  →  import { hasInjectionContext } from 'vue-demi'
vue-demi@0.14.10  →  lib/index.mjs 是 v3 分支，`export * from 'vue'`
vue-demi 位于【根 node_modules】
   → 向上解析 'vue' 命中【根 Vue 2.7.16】
Vue 2.7.16  →  不导出 hasInjectionContext（Vue 3.3+ 才引入）
→ 构建失败
```

关键点：
- `packages/patient-manage-app/node_modules/` 内有**自己的 Vue 3.5.46**，但**没有** pinia / vue-demi
- pinia 与 vue-demi 一路回退到根 node_modules，于是 `export * from 'vue'` 解析到根 Vue 2.7.16
- 根 Vue 2.7.16 是四个 legacy 端共用的，**不能**为了管理端把它换掉

**修复方案（已实测验证可行）**：给管理端补一份**局部** `vue-demi`：

```bash
cd /Users/yale/dev/tjProject/caring-patient-platform
cp -R node_modules/vue-demi packages/patient-manage-app/node_modules/vue-demi
cd packages/patient-manage-app/node_modules/vue-demi && node ./bin/vue-demi-switch.js 3
cd ../../.. && cd packages/patient-manage-app && npx vite build --mode prod
```

已实测：局部 `vue-demi` 的 `export * from 'vue'` 会正确命中同目录的 Vue 3.5.46，解析结果已验证。

> ❌ 错误方案：把根 vue-demi 切到 2.7 分支 —— 会让 pinia 跑在 Vue 2.7 上，与管理端本地 Vue 3.5 双 Vue 冲突。

### 🟡 阻塞 3：环境侧遗留（与代码无关）

- 宿主机已有一套 `caring-mysql` / `caring-redis` / `caring-nacos` 容器在跑（8 天 / 34 小时），但 **MySQL 密码未知**（`change-this-password`、`caring`、`root`、`123456`、`password` 均被拒）
- 该套 Nacos 里 **配置数为 0**（命名空间 `c5bec804-…` 与 `tenant=` 空查询均为 0），是遗留空环境
- `docker compose up` 因容器名冲突（`caring-redis`）失败

→ **解法**：用独立容器名/端口起新栈，不动宿主机现有容器。

### 🔴 演示的最大隐患：种子数据

`caring_init.sql` 有 **341 张表但仅 5 条 INSERT**（且全是 `c_auth_*` 权限表）：

- **无用户账号** → 无法登录
- **无租户数据** → `d_tenant` 空
- **无患者/医生/表单数据** → 五端列表页全空

**结论：即使服务全部起来，演示会看到一堆空列表。** 必须补一批种子数据（租户 + 角色 + 用户 + 若干患者/随访计划/表单记录）才能形成可演示的闭环。

## 六、组件补齐的具体建议

### 阶段 1：接线（先做，成本最低、收益立竿见影）

1. `packages/shared-components` 增加 `vue`/`vant`/`element-ui` peerDependencies
2. 四个 legacy 端的 `config/index.js` 加 alias：`'@caring/shared-components': path.resolve(__dirname, '../../shared-components/src')`
3. `src/main.js` 统一 `Vue.use(CaringComponents)`
4. 迁移 `arrt/` 表单域 19 个 + `headers/` 2 个 + `select`/`multiPicker`/`loading` 4 个 → **25 个组件，3 端以上完全一致，零改造**

### 阶段 2：管理端独立包

新建 `packages/shared-components-v3`（Vue 3.5 + Vant 3 + Vite），复用管理端已有的 3 个组件（`commonDialog` / `header` / `massPopup`）为起点。

### 阶段 3：渐进收敛

对其余 107 项候选按「用得最多的先上收」推进，每批保持四端构建绿。

### 建议配套

- 每个上收组件补单元测试（`shared-components` 现有 `test: jest` 脚本但**无任何测试文件**）
- 在 CI 加一条「禁止各端重复引入已上收组件」的检查
